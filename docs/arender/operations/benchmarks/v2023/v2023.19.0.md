# ARender 2023.19.0 — Performance

| Version under test | **ARender 2023.19.0** |
|---|---|
| Test date | April 2026 (re-run on the reference infrastructure for the v2026 comparison) |
| Test scope | **ARender Rendition backend only** (broker, converter, renderer, text handler) |
| Reference infrastructure | Three-node Linux Kubernetes cluster, 8 vCPU / 32 GB RAM per worker node |
| Tooling | Gatling, one-hour LOAD run |

This page reports validated performance figures for the ARender Rendition backend at v2023.19.0, captured on a reference infrastructure profile. It also serves as the baseline for the [ARender 2026 vs 2023 comparison](../comparisons/v2026-vs-v2023.md), conducted on the same infrastructure with the same scenario.

:::caution Scope reminder
These figures measure **the Rendition backend in isolation** — broker, converter, renderer, text handler. End-to-end performance in your own deployment also depends on the UI tier, your document source connector (DMS, ECM, S3, …), network, and authentication path. Use these numbers as a *Rendition-tier sizing reference*, not as a guaranteed end-to-end throughput.
:::

## Reference benchmark

On the reference infrastructure (three-node Kubernetes cluster, 8 vCPU / 32 GB RAM per worker), the Rendition backend sustains the following throughput over a continuous one-hour run:

| Indicator | Value |
|---|---|
| **Documents served per hour** | **~32,000** (8.89 docs/s) |
| HTTP throughput | 278.71 req/s |
| Total HTTP requests over the one-hour run | 1,003,914 |
| Error rate | **0%** |
| Global P50 | 17 ms |
| Global P95 | 131 ms |
| Global P99 | 269 ms |
| Mean response time | 35 ms |
| Max response time | 21,785 ms |

:::tip Sizing your Rendition tier
Assuming **20 documents opened per user during the busy hour** (≈ one document every three minutes — representative of moderate ECM and case-management workloads):

- This reference infrastructure handles **~1,600 active users** (32,000 ÷ 20) on the Rendition tier during the busy hour.

Substitute your own per-user document rate to size accordingly: `users on Rendition tier ≈ docs-per-hour ÷ docs-per-user-per-hour`. The other tiers of your deployment (UI, connector, DMS) need to be sized separately based on the same user count.
:::

## Per-endpoint latency

| Endpoint | Total requests | P50 (ms) | P95 (ms) | P99 (ms) | Mean (ms) | Max (ms) |
|---|---|---|---|---|---|---|
| Open_document_with_url | 32,039 | 18 | 30 | 42 | 20 | 433 |
| Get_document_layout | 32,039 | 228 | 486 | 1,656 | 294 | 21,785 |
| Get_3_images | 53,399 | 80 | 240 | 273 | 119 | 924 |
| Get_20_thumbnails | 224,279 | 25 | 54 | 73 | 28 | 612 |
| Get_3_pages_content | 630,119 | 15 | 41 | 62 | 19 | 688 |
| Evict_document | 32,039 | 10 | 24 | 38 | 12 | 188 |

The highest-volume endpoint, `Get_3_pages_content`, accounts for 62.8% of all requests (over 630k hits at 175 req/s) and serves them with sub-100 ms P99 latency. The `Get_document_layout` step shows the highest tail latency of the run — this was substantially improved in v2026.0.0 (see the [comparison](../comparisons/v2026-vs-v2023.md) for the delta).

## Stability

All 1,003,914 HTTP requests returned successfully with zero failures across the one-hour run. ARender v2023.19.0 sustained the target throughput for the full duration without functional errors.

## Methodology footnote

The reference benchmark uses a closed-injection Gatling run at 10 concurrent virtual users sustaining ~278.71 HTTP req/s for one hour, executing the standard per-document scenario described in the [benchmarks index](../index.md#methodology).
